# bank-poc — Digital Banking Platform

A proof-of-concept digital banking platform built as a learning project: a
**Spring Boot modular monolith** backend, a **React operator console**, and a
**React Native customer app**, all documented through a full SDLC paper trail
(planning → analysis → design → implementation → testing → deployment).

Everything here is illustrative — there are no real funds, customers, or
production deployments. The goal is to model how a regulated-grade fintech system
is designed and built end to end.

## The three apps

| App           | Stack                                  | Role |
|---------------|----------------------------------------|------|
| `apps/api`    | Java · Spring Boot 3 (modular monolith)| Core-banking REST API: auth, RBAC, accounts, wallets, ledger, transfers, KYC, audit, outbox events. The single source of truth. |
| `apps/web`    | React 18 · TypeScript · Vite           | Internal operator console. Thin, RBAC-gated client over `/v1`; every sensitive action captures an audited reason. |
| `apps/mobile` | React Native 0.74 · TypeScript         | Customer iOS + Android client. Thin, server-authoritative; secrets in the OS enclave; idempotent money transfers. |

Each app is **feature-first** and ships its own per-feature docs with functional
(FR) and non-functional (NFR) requirements traced to the code, under
`apps/<app>/docs/`.

## Architecture in one paragraph

A **modular monolith**, not microservices: one deployable Spring Boot app split
into clean internal modules. The money path (debit + credit + outbox) commits in a
single ACID transaction; side-effects (notifications, audit, analytics) flow
**event-driven** via a transactional outbox + broker. RBAC is enforced on the
server (`@PreAuthorize`); the clients only mirror it for usability. See
`sdlc/docs/07-tech-stack.md` for the full "why monolith, why event-driven"
rationale.

## Building & running

Each app builds independently — there is no top-level build.

```bash
# Backend (needs JDK 17+; H2 for tests, Postgres + RabbitMQ to run)
cd apps/api && ./mvnw clean test

# Operator console (Node 18+)
cd apps/web && npm install && npm run dev

# Mobile app (Node 18+, Xcode / Android SDK)
cd apps/mobile && npm install && npm run ios   # or: npm run android
```

> Dependencies (`node_modules/`, Maven `target/`) are not committed; they are
> regenerated by the commands above.

## Running with Docker

A `docker-compose.yml` at the repo root brings up the whole local stack —
Postgres, RabbitMQ, the API, and the web console — with one command. Each app
has its own `Dockerfile` under `apps/<app>/`.

### Prerequisites

- Docker Engine 24+ with the Compose v2 plugin (`docker compose`, not the legacy
  `docker-compose`).
- Ports free on the host: `8080` (web), `8081` (api), `5433` (postgres),
  `5672` / `15672` (rabbitmq), and `8082` (mobile Metro, opt-in).

### Start the default stack

```bash
docker compose up -d --build
```

Boot order is handled by health checks: `postgres` and `rabbitmq` come up first,
the `api` waits for them (runs Flyway migrations on start), then `web` serves the
SPA. Give the API ~30–60s on first boot.

| Service  | URL / endpoint                  | Notes |
|----------|---------------------------------|-------|
| web      | http://localhost:8080           | Operator console. nginx serves the static SPA and reverse-proxies `/v1` → api (same origin, no CORS). |
| api      | http://localhost:8081           | Spring Boot REST API. Health: `/actuator/health`. Also reachable same-origin at `http://localhost:8080/v1`. |
| rabbitmq | http://localhost:15672          | Management UI, `guest` / `guest`. |
| postgres | `localhost:5433`                | DB `bank`, user/pass `bank` / `bank`. Mapped to host **5433** to avoid clashing with a local Postgres on 5432. |

Verify everything is healthy:

```bash
docker compose ps
curl -s http://localhost:8081/actuator/health   # -> {"status":"UP",...}
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/   # -> 200
```

### Mobile (opt-in)

React Native has no browser target — a container can only run the **Metro JS
bundler**, which serves JavaScript to a physical device or emulator on the host.
Building the actual `.ipa` / `.apk` still requires Xcode / the Android SDK on the
host and cannot happen in the Linux container. Metro lives behind a Compose
profile so it stays out of the default `up`:

```bash
docker compose --profile mobile up -d --build mobile
# Metro dev server: http://localhost:8082  (status: /status)
```

### Common commands

```bash
docker compose logs -f api        # tail one service
docker compose ps                 # status of all services
docker compose down               # stop, keep the postgres volume (data persists)
docker compose down -v            # stop AND wipe the postgres volume (fresh DB)
docker compose build --no-cache api   # force a clean rebuild of one image
```

### Image design

- **api** — multi-stage: Maven + Temurin 21 to build the fat jar, then a slim
  `temurin:21-jre` runtime running as a non-root user.
- **web** — multi-stage: Node 20 builds the Vite bundle, then nginx serves the
  static `dist/` and proxies `/v1` + `/actuator` to the api (`nginx.conf`).
- **mobile** — Node 20 running the Metro bundler.

> Two pre-existing repo defects had to be fixed to make the stack run end-to-end
> against real infrastructure (the in-repo tests use H2 / never start Metro, so
> neither surfaced before): migration **`V7__currency_varchar.sql`** aligns the
> `currency` columns (`CHAR(3)` → `VARCHAR(3)`) with the JPA mapping so Hibernate
> `ddl-auto: validate` passes on Postgres; and three missing React Native dev
> dependencies (`@react-native/metro-config`, `@react-native/babel-preset`,
> `babel-plugin-module-resolver`) were added to `apps/mobile/package.json` so
> Metro can start.

## Deployment & going to production

The Compose stack is for **local development only** — single-node, default
credentials, dev JWT keys. It is not a production topology. The documented target
architecture (AWS EKS + GitOps/Argo CD) lives in the SDLC chapters; below is the
practical gap between "runs on my laptop" and "safe to deploy."

### Build & publish images

```bash
# Tag with an immutable version (git SHA), not :latest, for real deploys.
docker build -t <registry>/bank-api:$(git rev-parse --short HEAD) apps/api
docker build -t <registry>/bank-web:$(git rev-parse --short HEAD) apps/web
docker push <registry>/bank-api:<tag>
docker push <registry>/bank-web:<tag>
```

The web image bakes config at **build time** (Vite `import.meta.env`). To point
the SPA at a real API, build with `VITE_API_BASE_URL` set, or keep the relative
`/v1` default and front both with an ingress that routes `/v1` to the api.

### Run the API in `prod` mode

Activate the prod profile and supply every secret via the environment / a secrets
manager — never bake them into an image or commit them:

```bash
SPRING_PROFILES_ACTIVE=prod
DB_URL=jdbc:postgresql://<host>:5432/bank
DB_USER=...            DB_PASSWORD=...
RABBITMQ_HOST=...      RABBITMQ_USER=...   RABBITMQ_PASSWORD=...
JWT_PRIVATE_KEY_PEM=...   # real signing keypair; dev generates an ephemeral one
JWT_PUBLIC_KEY_PEM=...
```

The `prod` profile (`application-prod.yml`) turns off SQL echo, drops trace
sampling to 10%, and quiets logging. JWT keys left blank generate a throwaway
dev keypair — fine locally, unacceptable in prod (tokens won't survive a
restart and aren't shareable across replicas).

### Production checklist (gap from this POC)

- **Secrets** — move `DB_*`, `RABBITMQ_*`, `JWT_*` into a secrets manager
  (AWS Secrets Manager / Vault). Rotate the dev `bank/bank` and `guest/guest`
  credentials.
- **Database** — use a managed, backed-up Postgres (e.g. RDS) with TLS; not the
  in-compose container. Flyway runs migrations on boot — gate this behind a
  controlled release step for multi-replica rollouts.
- **Message broker** — managed/HA RabbitMQ with real users, vhosts, and TLS.
- **TLS everywhere** — terminate HTTPS at the ingress/load balancer; the mobile
  client pins public keys (`TLS_PIN_*`), so pins must match the real cert chain.
- **Scaling & resilience** — run multiple stateless api replicas behind a load
  balancer; wire the `/actuator/health` liveness/readiness probes (already
  exposed) into the orchestrator.
- **Observability** — scrape `/actuator/prometheus`, ship logs, and point the
  OTel tracing bridge at a real collector.
- **Images** — pin base images by digest, scan for CVEs, run as non-root (the api
  image already does), and deploy immutable version tags via GitOps.

## Status

Proof of concept / learning project. Not for production use. The Docker Compose
stack is a working local environment; the production guidance above describes the
gap to a real deployment, not a turnkey one.
